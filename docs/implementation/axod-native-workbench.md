# Axod-only native workbench cutover

## Acceptance bar

The operator wants `dist/Axo.app` to replace the former daily workbench so Axo can be used to develop Axo. Source builds, metadata browsing, and cloud registration do not establish that parity. Never retire a working client merely because its replacement builds. Repackaging does not authorize stopping accepted daemon/Pi work.

## Current workflow audit

The [supported-workflow inventory and acceptance plan](supported-workflow-inventory.md) audits source `23be4c9`, traces native/local/cloud/phone workflows and existing file authority, distinguishes component evidence from actual-surface acceptance, and records the user's resolved scope decisions. Empty startup automatically creates a Pi-left/shell-right session; standalone uses HOME and projects use the selected folder. Safe URLs, appearance import, all-action shortcuts, menu-bar controls, iOS push and basic Pi usage display are included. The phone caches its catalog but disables offline-machine session interaction. Its source baseline is not a claim that the live helper or deployed API matches the packaged app.

## Ordered implementation

1. **Native work records:** workspace/session create and rename, captured destinations and revision, durable command reconciliation without redispatch. New workspace uses the standard macOS directory picker: selection by the local user is approval, not a daemon profile allowlist. Persist the selected directory through a local-only typed boundary; cloud callers must not acquire arbitrary-path authority. Support standalone sessions with no workspace, starting at the user's captured home directory and grouped separately in the sidebar; never synthesize a hidden workspace. Wire menu, toolbar and sidebar actions through one path. Installed ambient Pi remains the runtime dependency, not a bundled engine.
2. **Managed Pi:** fresh admission/exact resume, branch-aware history, send/steer/cancel, owned questions, tool details, per-conversation drafts, source-bound observation and reconnect. Restore metadata only; never replay messages or adopt previous processes.
3. **Terminal data plane:** implement a separate bounded local attachment protocol over actual owned PTYs, not terminal bytes inside metadata/cloud RPC. Prove input, output, resize, detach, EOF, backpressure, renderer capability and IME. Reuse the existing native terminal/split foundations; backlog is not a VT snapshot.
4. **Pane lifecycle:** typed local add/remove, Cmd+D/Cmd+Shift+D splits, captured focus, Cmd+W exact semantics, detach versus termination, durable completion-gated removal, state restoration and sibling isolation.
5. **Workbench parity:** window-scoped selection and focus, independent windows over shared work, keyboard/menu actions, persistence, notifications, appearance. Inventory archive/duplicate, files/attachments and voice against daemon capabilities; implement missing authority rather than adding nonfunctional UI or reviving the deleted bridge.
6. **Service updates:** About exposes bundled and actual running versions. On opening a newer app, automatically replace an older helper only through an atomic idle/quiesce upgrade handshake; defer while accepted work is active. There is no Replace Older axod button or migration confirmation modal. Helpers without the handshake cannot provide atomic idle proof; preserve their work and perform ownerless registration repair automatically once the validated lease proves absence. An enabled SMAppService is not proof that launchd resolves the current bundle/helper. Check the resolved executable when validating a live update; stale registrations can still resolve moved/trashed bundles. No automatic unregister/restart of an owner with accepted work. Establish explicit, safe service repair/update semantics.

## Current evidence and gaps

- Rust CLI/local/cloud managed Pi and shell lifecycle have isolated acceptance; the native app has metadata browsing and initial managed chat controls.
- The first native workspace/session creation pass uses captured target/revision, shared validators, saved unresolved command IDs and explicit read-only reconciliation. Native folder selection now replaces the rejected profile picker. The local-only `axo.workspace.createLocal` accepts a parsed absolute `directoryPath`, requires its canonical directory to remain usable, and persists it in the existing private work store and immutable receipt. No `profiles.json` entry is required. Cloud callers cannot use this method; the existing cloud/profile creation contract is unchanged. Actual `axo`/`axod` fixture acceptance covers creation with an empty profile map, session metadata in that workspace, receipt replay/collision and restart. The native explicit creation path now starts Pi; local workspace plus its first session commit atomically. Standalone sessions capture the daemon user's home without a hidden workspace. New Session requests creation directly, without a name prompt or progress modal; metadata success selects the session before Pi readiness, with failure/uncertainty kept inline. The default installed-helper policy loads the bundled Axo adapter into ambient Pi using captured login-shell PATH, without configured profiles. Project-local executable resources are ignored by default (`--no-approve`); ordinary user Pi configuration and context discovery remain in Pi. `axo_set_title` names the canonical conversation through Pi's public API, with bounded display metadata projected into the sidebar. Rename remains incomplete. Sidebar and keyboard/menu entry points share the initial path. This is source/build progress, not native interaction or crash-durability acceptance.
- Settings must contain General, Keybindings and Voice & Transcript only. About Axo is a compact native application-menu window with the tagline, app/bundled-daemon version, build, commit and status. Do not expose duplicate daemon or startup pages, and remove the bottom-right Refresh button.
- Swift session parsing now includes typed, bounded shell-pane projections and checks session/pane ownership, unique IDs and exact terminal references. Previously Swift rejected the daemon's `shellPanes` field; empty-catalog builds did not expose this.
- **Still incomplete:** New Session must immediately open two actual terminal splits: Pi left and an independently starting regular shell right, even while Pi admission is pending. No creation modal, Open Session button, or placeholder text surface is an acceptable substitute. Local terminal attachment is a backend gap, not just an unwired view. A running PID or prepared start is not usable Pi; current live uncertain starts were inspected read-only and were not retried or killed.
- Archive/duplicate, attachments and explicit runtime/daemon stop need backend capability work.
- API deployment and physical iOS installation succeeded during the baseline deployment. Mac packaging succeeded, but live helper replacement was **not** verified: the registered helper resolved a trashed older app and did not expose `axo.host.get`. Do not call this a completed live Mac upgrade or confirmed production cloud registration. Native startup now attempts one ownerless registration repair under a validated exclusive `owner.lock` lease; it never unregisters an active owner based on discovery failure. The newer-app/live-older-daemon comparison and local-only, exact-plan idle/quiesce handshake now have isolated tests, including active-work deferral. Normal connection/observation performs the update automatically; actual ServiceManagement handoff and current live startup remediation remain separate, unverified acceptance.

## Validation

Require typed request/result and captured-target tests; actual public-RPC/PTY acceptance; native build and signed `dist/Axo.app`; then explicit human/native operational drills. Exercise create/start/send/tool/history, pane input/split/resize/close, window detach/restore and reconnect without duplicate execution. Keep live deployment, authentication, Accessibility and device acceptance distinct from compilation and fixtures.
