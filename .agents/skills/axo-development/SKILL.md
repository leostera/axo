# Axo development

Keep Axo-specific workflows and operational knowledge in `.agents/skills/axo-*`. Improve an existing relevant skill or add a focused skill as repeatable practices emerge. Do not put these project notes in the personal memory repository. Skills should describe how to work, not accumulate transient test logs, process IDs, backup paths, or a second conversation history. For native Mac scenes, windows, sidebar/detail UI, settings, and AppKit boundaries, follow [axo-macos-native-apps](../axo-macos-native-apps/SKILL.md); for delivery, also follow the sibling packaging skill.

## Integration boundary

Axo extends **the user's ambient vanilla Pi through installable extensions and public APIs**. Pi is a runtime dependency, not an Axo-vendored/bundled engine. Resolve a captured normal PATH launcher or explicit operator-selected executable; ignore npm-injected project `node_modules/.bin` and never silently fall back to the repo's Pi devDependency, auto-install or auto-upgrade. Validate supported public capabilities/readiness and report missing/unsupported installations clearly. Development Pi type declarations are not the execution origin; real integration tests must exercise the ambient CLI. The product path is Axo public RPC → Rust daemon → daemon-owned native PTY → ambient Pi's interactive TUI with an installed Axo control extension, using public Pi APIs in that same process. Do not add a separate `pi --mode rpc` execution path without an explicit product use case. The Rust CLI must exercise the same addressed Axo RPC path as the Mac/cloud clients, not talk directly to a different Pi mode. No attached Mac window is required for a TUI to keep running in its daemon-owned PTY. `axod/pi/README.md` records this boundary; `npm run test:pi-discovery` checks dependency discovery only, not execution/admission acceptance. `npm run test:pi-interactive` exercises real ambient TUI + production Rust native PTYs with a public control extension and owned loopback provider; that fixture adapter is not the public WebSocket/product-CLI chat path. Separately, `axod/tests/managed_public.rs` now joins actual `axo`/`axod serve` to real ambient Pi, and a Rust-owned cloud peer through an actual isolated Worker admits/executes an independent Pi. Node may host the Worker fixture, not daemon/Pi orchestration; private synthetic assertions must not enter argv/logs. Keep initial acceptance separate from full RFD/Mac readiness. See `axod/MANAGED_PI.md` for policy/contracts/evidence limits. Actual interactive abort/queues/dialog behavior must be verified there, not inferred from the discarded headless mode. Pi owns execution, queues, transcript persistence, and active conversation/branch. Do not patch Pi, use private runtime APIs, invent transcript records, or infer execution/steering identities from terminal text or timestamps. State observations and notifications are not an execution broker.

Capture explicit session, conversation, pane, and generation destinations before asynchronous operations. Revalidate them before applying a result; never fall back to the globally selected session. Restoring terminals must not replay prompts or shell commands. Read-only history/catalog operations must not execute work.

Reuse the pinned upstream Ghostty split implementation and preserve its MIT provenance. Do not modify ignored vendor sources or introduce a competing split geometry engine.

Use the current RFDs and repository tests for detailed contracts, especially `docs/rfds/RFD0003-workspaces-sessions-and-search.md`. Keep honest distinctions between implemented local features and unfinished addressed phone routing/broker work; search remains deferred until the foundation is complete.

## Axod-only Mac migration

The standalone Rust daemon is `axod/`. Implement and harden it there, not in new POCs. Pi-loaded extension code belongs in `pi-axo/` and uses TypeScript/public Pi APIs; it is not daemon implementation. Keep daemon/CLI integration orchestration and process fixtures in Rust; existing TypeScript daemon fixture orchestration is transitional, not the target architecture. Its private runtime journal is not a second writer to the existing Mac workspace registry. Keep its processes/state isolated from the live application while developing it.

The operator selected an Axod-only Mac app for newly built/relaunched bundles. Build Mac UI around the existing workbench design, with local RPC through `AxoProtocol`/`AxoCore` and the bundled `axod`; do not extend the legacy bridge/execution path or add compatibility import. Unsupported workbench features may be absent until their Axod capability exists.

This is not a live-session migration. Use the separate private Axod state directory `~/Library/Application Support/Axo/Axod` (no versioned directory suffix), never import the legacy workspace registry or Pi histories, never adopt historical PIDs, and do not stop/restart the already-running app or its sessions without separate consent. The new Axo app registers itself as a user-level login item via `SMAppService`; it does not install an `axod` LaunchAgent/LaunchDaemon. Keep the iOS and legacy service/file lanes independent until separately requested. Axod's runtime journal and work-record store remain separate authorities; never create two writers during any future handoff.

Use neutral relationship terminology: **host/child endpoints** for PTYs, **controller/worker** or **leader/follower** where appropriate. Preserve upstream API names only where required for compatibility.

## Private API and protocol development

Owned Rust protocols should deserialize into closed native enums/structs at the boundary and route by exhaustive matches, not inspect `serde_json::Value` keys or stringly typed method names. Use distinct identity types and request-specific response expectations. Isolate genuinely open-ended Pi/plugin documents in explicitly opaque payload types; they must not become routing or execution authority.

Keep the next private control-plane iteration in `sites/api.axo.leostera.dev/` and shared contracts in the proper `@axo/protocol` package under `protocol/`. JavaScript consumers import its compiled package exports, not sibling TypeScript source. Preserve the current `service/` lane and its file/relay authority until a separately coordinated migration.

Install/build/test the protocol package independently before the new API. Follow their READMEs for `cf` build/type generation, isolated Node/Miniflare tests and the real-`axod` network suite. Use the same supported workerd compatibility target; Miniflare v5 persistence uses `resourcePersistencePath`, and cold-runtime/hibernation tests must establish actual storage/socket recovery. Library request correlation is not durable command execution identity or DO recovery state.

`axod serve` now uses loopback JSON-RPC and private `local-endpoint.json` discovery, not Unix IPC. Local credentials were explicitly deferred: native Host/path/no-Origin guards are browser restrictions, not OS-user authorization. Keep Access as the existing cloud edge gate without introducing application accounts, enrollment or user-management scaffolding. Use the shared dispatcher/profile policy for local/remote parity; do not add a native-side legacy-envelope shim or assume terminal data/Pi APIs are exposed by the metadata/approved-profile/work-record slices.

The private daemon work store is `work-records.json`, opened under the same owner lock as its runtime journal. It is not permission to import or mutate live Mac work records. Metadata create/rename/read must not launch or invent Pi chats; generic runtime observations remain distinct from admission. Preserve shared execution/work/Pi command admission, immutable receipts, source/revision/filter-bound cursors and cross-domain persistence fencing. Managed Pi policy is an explicitly validated private `--pi-config` (directory-profile approval, session root, installed extension, ambient launcher); callers never supply cwd/argv/session paths. `pi-state.json` contains intent fingerprints/dispositions/bindings, not prompt/history bodies. Pi alone writes canonical JSONL. Fresh/resume intent, current versus runtime birth host generation, live versus explicit stopped read mode and source/branch-bound cursors must remain distinct. Cooperative leases are not proof against unmanaged writers, and missing/uncertain outcomes never permit replay. Managed stopped reads, exact resume and stopped/failed admission must use the Manager's exact durable completion/resource proof, never merely a visible process exit or cached Pi readiness. Explicitly release cooperative flock ownership before FD closure so transient fork copies cannot prolong a released lease; test duplicated-descriptor ownership without signaling a process.

Shell panes use local-only `axo.session.pane.add/remove`, not separate create/start methods. Add is explicit create-and-launch of a fresh approved shell PTY (Cmd+D / Cmd+Shift+D); remove is explicit termination of the captured owned runtime plus proof-gated tombstoning (Cmd+W). Renderer detach/client quit remain non-destructive; split direction/focus stay native-local. `pane-state.json` participates in shared command/storage fencing and retains original receipts/tombstones; neither generic launch nor reconciliation may replace/replay a pane. Require the exact runtime and a Manager completion witness, never caller-claimed completion or historical PID signals. Shared protocol exports `localMethods` separately from cloud `remoteMethods`; do not silently widen cloud exposure. See `axod/PANES.md`.

For daemon hardening, run `npm --prefix protocol run test:properties` and `npm --prefix sites/api.axo.leostera.dev run test:properties` alongside Rust and real-route tests; use `PROPTEST_CASES`/`PROPTEST_RNG_SEED` for bounded completion-model campaigns. Bound actual single/batch response wire bytes, preserve IDs on post-dispatch uncertainty and exercise incremental serialized reply groups. Keep shrinking/replay without payload diagnostics and distinguish model/property fuzzing from coverage-guided fuzzing or actual crash/power-loss acceptance; see `axod/tests/README.md`. Differential oracles must call production codec/admission code and explicitly forbid mutations, not fake Pi execution. Retain seed/path replay and minimal synthetic regressions without logging payload bodies. Inject persistence faults at commit boundaries and distinguish memory fencing, same-kernel reopen and actual power-loss durability. Parallel PTY forks can briefly inherit other test roots' CLOEXEC locks: bounded waiting is allowed only for disposable fixture ownership, never commands/corruption or production replay. A passing generated suite is not production-hardening evidence.

For packed-package consumer tests, create an explicit fixture `package.json` and assert `npm prefix` resolves to that fixture **before** any install. An empty temporary cwd can make npm walk to an unrelated ancestor project. Keep package tarballs, credentials and daemon state in owned disposable fixtures; never use live app state or deployment credentials for isolated tests.

## AxoPhone sidebar design contract

When refining the compact iPhone Sessions menu, use the supplied ChatGPT sidebar screenshot as a proportional reference:

- Keep the Sessions list underneath the chat surface. Reveal it by translating the foreground chat right; use a width-derived reveal distance of about 79% of the available compact viewport, capped near 360 pt, and make the exposed sidebar the same width.
- Align sidebar content to shared rails: roughly 32 pt leading and 24 pt trailing. Keep search and Settings on the trailing rail.
- Use text-only session rows, grouped by workspace. Inset the selected-row background about 10 pt from each edge; use a roughly 44 pt row with a 38 pt selected pill, and inset the label so its leading edge aligns with the 32 pt content rail. Reserve symbols for actions, not session identity.
- Keep the header compact, use 44 pt controls, and align the bottom New Session and Settings actions to the same rails.
- Extend a secondary-system-surface backplate behind the foreground chat through the status-bar and home-indicator safe areas. At full reveal, a tertiary-system-surface overlay near 0.64 opacity over chat content lands near the reference's `#1b1b1b` background while muting bright content to roughly `#78`; keep that overlay confined to the shifted chat, never the sidebar. Do not snap the color change only after the gesture ends. Let corner rounding (about 42 pt on the supplied phone) and shadow track the same progress.
- Keep workspace creation out of the scrolling session list; expose it alongside New Session in the footer action menu so the list remains visually focused on sessions.
- While the menu is open, dim and disable the foreground chat, including scroll and accessibility interaction, while keeping the exposed sidebar interactive. Preserve a reverse-swipe close path that can begin on the visible chat surface as well as the sidebar.
- These are reference starting measurements, not device-wide constants. Derive the reveal from available geometry and verify Dynamic Type, landscape, and narrow layouts. User-facing terminology is **Sessions**, never “Playground”; retain that spelling only in compatibility code when required by stored data.

## Validation and delivery

- Make frequent, coherent, validated Conventional Commits and push proactively.
- Follow the sibling [axo-macos-packaging skill](../axo-macos-packaging/SKILL.md) whenever a change affects the Mac app or its Pi bridge. **Always deliver an updated `dist/Axo.app`**, not only a DerivedData build.
- Packaging is not permission to restart the live Mac/Pi processes or install/relaunch the physical phone. Ask separately and preserve ongoing work.
- Never bypass denied Accessibility permissions. Synthetic isolated tests are useful but do not prove live UI, macOS notification-banner/click, or physical-device acceptance.
- Report source/build/package/live status accurately. Document public API gaps rather than disguising partial coverage as complete behavior.
